# Store POC specification fields on kb_knowledge

For the team POC, Catalog Test Specifications will be Knowledge Articles in a dedicated Knowledge Base, with the structured Catalog Item, schema-version, User Criteria, and Representative Test User fields added directly to `kb_knowledge`. This avoids the Knowledge Management Advanced plugin, native article-template metadata, and a second synchronized record, at the accepted cost of adding ATF-specific columns to the shared Knowledge table and requiring a future migration if the specification grows into a production-scale model.

The application will create and own the dedicated **Catalog Test Specifications** Knowledge Base and bind generation directly to that application record. The POC will not let an administrator select an existing Knowledge Base, store its identity in a System Property, or resolve it by title; this removes configuration and ambiguous lookup logic at the accepted cost of coupling the generator to one application-owned Knowledge Base.

The application will expose a **Catalog Test Specifications** module that opens a `kb_knowledge` list filtered to the application-owned Knowledge Base and uses a dedicated Catalog Test Specification form view. The view groups specification identity, permission-design fields, and optional human notes while leaving Article Body non-authoritative; generation never parses it. A separate **Create New** module in the same **ATF Generation** application menu opens a new `kb_knowledge` record directly with the dedicated view and application-owned Knowledge Base query because Australia routes the OOB list action through the Knowledge Center article wizard, which drops the dedicated Platform form view. Creation deliberately uses no scoped list UI Action or view-specific UI Action mapping.

The POC will leave these shared-table fields non-mandatory and will not add a conditional UI Policy, Data Policy, publication check, or generator-side completeness validation. A Current Specification that reaches generation is assumed to contain all required values; structurally incomplete Published records are outside the demo contract. This deliberately minimizes authoring and validation logic rather than attempting to make the shared `kb_knowledge` schema safe for production use.

The six physical columns use complete, readable scoped names rather than abbreviations: `x_gemjp_atf_genera_catalog_item`, `x_gemjp_atf_genera_schema_version`, `x_gemjp_atf_genera_accessible_criteria`, `x_gemjp_atf_genera_accessible_user`, `x_gemjp_atf_genera_inaccessible_criteria`, and `x_gemjp_atf_genera_inaccessible_user`. Keeping Accessible and Inaccessible explicit preserves the domain language in scripts and queries without adding runtime logic.

Selecting **Create New** from the **ATF Generation** application menu will open the Platform form directly, bypassing the generic Knowledge Center article wizard, and prefill the application-owned **Catalog Test Specifications** Knowledge Base while leaving the field editable. Knowledge lists retain their OOB **New** behavior. The POC deliberately trusts the Test Designer instead of adding UI or server-side enforcement; if the field is changed to another Knowledge Base, that record is outside the generator's eligible Specification set.

For the team demo, the same trusted Test Designer persona will author, edit, and immediately publish Specifications as well as invoke ATF Generation; no separate Specification Author persona is introduced. The OOB `atf_test_admin` role remains the gate for **Create ATF**, but it does not itself grant Knowledge authoring or article-versioning authority. The demo Test Designer user will therefore also be added to the **Managers** of the application-owned **Catalog Test Specifications** Knowledge Base. This uses OOB, Knowledge-Base-scoped authority instead of broad Knowledge administration or custom ACL logic, at the accepted cost of updating the Managers list when the demo user changes.

The dedicated form view will contain only three sections: **Specification Identity** (Number, Knowledge Base, Workflow State, Short Description, Catalog Item, and Schema Version), **Permission Design** (the two User Criteria and two Representative Test User references), and **Human Notes** (Article Body). Standard Knowledge fields outside that set remain on `kb_knowledge` but are omitted from the view. Short Description and Article Body are human-facing only; generation consumes only the structured identity, compatibility, and permission fields.

The module will expose one list filtered only to the application-owned Knowledge Base and will add no lifecycle predicate. Its columns are Number, Short Description, Catalog Item, Workflow State, Schema Version, Updated, and Updated by, ordered by Updated descending. OOB Australia Knowledge access permits the manager-only Test Designer to work with Draft and Published records but restricts Retired articles to administrators and knowledge administrators. The POC accepts that a Retired Specification leaves the Test Designer's authoring list rather than granting broad `knowledge_admin` authority or adding custom ACL logic. Reusing OOB list filtering and security avoids lifecycle-specific modules or navigation while keeping the authoring list independent of the generator's stricter Published-only query.

No consolidated post-install checklist will be created for the POC. Updating the Knowledge Base Managers list when the demo Test Designer changes remains a manual team responsibility recorded in the design ADRs rather than a separate deployment document or runtime configuration mechanism.

## Verified implementation facts

- The installed ServiceNow SDK 4.8.1 `Table` API supports adding fields to an out-of-scope table with `Table({ augments: 'kb_knowledge', schema: ... })`; its build emits only the owned `sys_dictionary` records and no replacement `sys_db_object`.
- The installed SDK `Form` and `List` APIs emit the dedicated `sys_ui_form`, `sys_ui_section`, `sys_ui_element`, `sys_ui_list`, and `sys_ui_list_element` metadata used by this authoring surface. SDK 4.8.1 does not merge fields declared by a same-build table augmentation into the `Form` API's static table type, so each of the six augmented field-name literals has a local type escape. No cast surrounds the form, table, view, layout structure, or OOB fields, and generated XML retains the literal augmented field names.
- Australia manual acceptance showed that the OOB global **New** UI Action (`80c8c3a60a0a0b34003364513f7d9d27`, action name `sysverb_new`) invokes the Knowledge Center article wizard even from the dedicated list. A direct `kb_knowledge.do?sys_id=-1&sysparm_view=catalog_test_specification&sysparm_query=kb_knowledge_base%3Dad51c081c2bb45cbbf74bc83396cbb05` request renders the intended form and defaults correctly. A first view-specific replacement attempt failed in two observable ways: both OOB and scoped **New** buttons rendered, and the scoped action raised `No records selected`. Post-deployment query confirmed SDK 4.8.1 emitted the scoped banner action with `list_action=true`; the ServiceNow form also displayed its Table field as blank despite the built XML containing `kb_knowledge`. Ticket 02 therefore removes that action and both view mappings and uses the proven URL in a `DIRECT` **Create New** module.
- SDK 4.8.1 Fluent ATF can navigate to application modules. The packaged Ticket 02 test now navigates first to the dedicated list module and then to **Create New**, allowing the authoring route and target form to be exercised without a list-banner UI Action step. The actual **ATF Generation → Create New** route remains a required post-deployment Australia manual acceptance check; metadata success alone does not close `FORM-01`.
- Australia instance queries verified the active, unlocked OOB **System Administrator** user (`6816f79cc0a8016401c5a33be04be441`) and multiple active OOB Knowledge Bases already use that record as owner. Ticket 02 uses it as the application-owned Knowledge Base's technical metadata owner rather than reusing Ticket 01's Representative Test User fixture. Knowledge Base Managers remain a separate, manually maintained list; the manager-only Test Designer does not receive general Knowledge administration authority.
- The built module is a `LIST`-type `sys_app_module` with table `kb_knowledge`, dedicated view `catalog_test_specification`, and encoded query `kb_knowledge_base=ad51c081c2bb45cbbf74bc83396cbb05^ORDERBYDESCsys_updated_on`. The only query condition is the application-owned Knowledge Base; `ORDERBYDESC` controls presentation and does not exclude a lifecycle state. OOB ACL behavior remains authoritative for which lifecycle rows the current persona may read.
- ServiceNow Australia documentation states that Knowledge Base Managers automatically receive the base-scoped `knowledge_manager` role, while only administrators and knowledge administrators can view Retired articles. The POC preserves the manager-only Test Designer and accepts that OOB Retired visibility boundary instead of adding `knowledge_admin` or custom ACLs.
- Australia instance queries verified the OOB Flow Designer records **Knowledge - Instant Publish** (`2222030614f75210f8779da9137d35b3`) and **Knowledge - Instant Retire** (`ea32fac859c02210f877a8ba01addda2`) as active, Published, `flow`-type records at version 2. Ticket 02 binds `kb_publish_flow` and `kb_retire_flow` directly to those records, leaves the legacy `workflow` and `retire_workflow` fields blank, and creates no scoped lifecycle automation. The executable Ticket 02 acceptance test verifies that deployed configuration together with the absence of scoped UI and Data Policies; the OOB Publish/Retire interactions and Knowledge Base Manager authority still require real-instance acceptance.
